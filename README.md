# ANPR Узбекистан

Сервис распознавания автомобильных номеров Узбекистана: **YOLO11** находит пластину на кадре,
собственный `TPS-ResNet-BiLSTM-CTC` читает текст, а поверх — доменные правила форматов номеров УЗ,
определение цвета фона, трекинг с голосованием по кадрам, журнал событий, REST и WebSocket
на FastAPI.

Точность на реальных фото — **72/80 (90%)** при детекции 100%, замер воспроизводится одной
командой (см. [ниже](#измеренная-точность-на-реальных-номерах-уз)). Все числа в этом README
получены прогонами, а не оценками.

```
кадр ──► YOLO11n-plate ──► кроп ──► TPS-ResNet-BiLSTM-CTC ──► правила УЗ ──► трекинг+голосование ──► событие
         ~42 мс/кадр               ~60-90 мс/пластина        формат/цвет     стабильный номер      SQLite + WS
```

## Чего в репозитории нет

Веса в git не лежат — только код. Перед запуском нужны два файла:

| Файл | Размер | Откуда |
|---|---|---|
| `models/yolo11n-plate.pt` | 5 МБ | `python -m tools.fetch_yolo` скачает сам |
| `best_accuracy.pth` | 196 МБ | распознаватель номеров УЗ, положить в корень проекта |

`best_accuracy.pth` — дообученный `TPS-ResNet-BiLSTM-CTC` с двумя CTC-головами; в репозиторий
не помещается (лимит GitHub — 100 МБ на файл), храните в Git LFS, релизах или рядом с деплоем.
Без него сервис не поднимется: на старте он проверяет число классов и наличие голов и падает
с понятной ошибкой, а не молча.

Так же не попадают в git: `data/` (база событий, снапшоты, скачанные выборки для замеров),
`.env` с локальными настройками.

## Что внутри чекпоинта распознавателя

Распознаватель обучен автором проекта на собственном датасете узбекских номеров: сбор,
ручная чистка, обучение, замеры. Код обучения был утерян, от модели остался только файл
весов — ни конфига, ни charset, ни размера входа, только 246 тензоров. Поэтому архитектура
восстановлена по ключам и формам весов и собрана заново 1:1 в
[app/core/model.py](app/core/model.py):

| Блок | Что это |
|---|---|
| `Transformation` | TPS Spatial Transformer (RARE), F=20 контрольных точек, выпрямляет в 32×100 |
| `FeatureExtraction` | ResNet из deep-text-recognition-benchmark, вход **1 канал** (grayscale) → 512 |
| `SequenceModeling` | 2 × BiLSTM(hidden=256) → 256 |
| `Prediction` | **две** CTC-головы `Linear(256 → 95)`: `head_anpr` и `head_ctype` |

То есть это `TPS-ResNet-BiLSTM-CTC` с двумя выходами — именно так «две модели EasyOCR»
и оказались объединены: общий энкодер, две независимые головы.

**Charset.** 95 классов = 1 CTC-blank + 94 символа, что однозначно указывает на
`string.printable[:94]` (цифры + строчные + ЗАГЛАВНЫЕ + пунктуация), класс 0 = blank.
Проверка по весам подтверждает: у «живых» классов bias около нуля, у никогда не встречавшихся —
заметно отрицательный.

- `head_anpr`: живые классы — цифры `0-9` и заглавные `A-Z`, **кроме `I`** (её в номерах УЗ нет).
  Строчные буквы и пунктуация мертвы. Отсюда `LETTERS` в [plate_rules.py](app/core/plate_rules.py) — без `I`.
- `head_ctype`: живые классы — только цифры, `H` и `M`. То есть эта голова выдаёт строку
  из цифр и этих двух букв.

**Что делает `head_ctype` — измерено на 40 белых номерах с platesmania:**

| Проверка | Результат |
|---|---|
| `ctype` совпал с текстом номера | 0/40 |
| `ctype` начинается с кода региона номера | 34/40 |
| похожесть на цифры номера / на весь номер | 0.67 / 0.56 |
| буквы во всех выводах | только `H` и `M` |
| одна и та же пластина на двух фото | выводы **разные** |

То есть на белых номерах вторая голова читает ту же последовательность символов, но
своим алфавитом, «оцифровывая» буквы: `01 A 135 MC` → `01013540`. Это не категория и не
стабильный код — для одной пластины на разных фото результат разный. **На обычных номерах
она бесполезна, и вот почему:**

**Модель читает все типы номеров** — обычные (физлица + юрлица), жёлтые и зелёные. Головы при
этом разные по алфавиту, и это, похоже, объясняет, как «две модели EasyOCR» были объединены:

| Голова | Алфавит | Каким номерам он соответствует |
|---|---|---|
| `head_anpr` | цифры + `A-Z` без `I` | обычные: `01 A 111 AK`, `01 006 DFA` |
| `head_ctype` | цифры + `H` + `M` | цветные: `01 M 018461` (зелёный), `01 H 018461` (жёлтый) |

Цветные номера УЗ устроены как **регион + одна буква серии + 6 цифр**, и буква там ровно из
набора второй головы: зелёные — электромобили ([введены в ноябре 2021](https://www.gazeta.uz/ru/2023/03/27/hybrid-cars/)),
жёлтые — транспорт иностранцев (1 буква и 6 цифр на жёлтом фоне). То есть `{цифры, H, M}` —
это в точности алфавит жёлтых и зелёных, а не случайный набор.

Наблюдение на зелёном номере `01 M 018461` в ту же сторону — вторая голова взяла последний
символ уверенно там, где основная ошиблась:

```
head_anpr  : 01M01846A   последний символ — буква 'A', уверенность всего 0.53
head_ctype : 01M00018461 последняя цифра '1' верная (лишние нули — артефакт CTC)
```

Поэтому вывод второй головы подмешивается в кандидаты для жёлтых и зелёных — обе головы
считаются одним форвардом, так что это бесплатно:

```bash
ANPR_TYPE_HEAD_COLORS=yellow,green   # включено по умолчанию
```

Кандидат побеждает только если укладывается в формат номера УЗ, поэтому механизм безопасен:
на 80 белых номерах результат одинаковый (72/80) и с опцией, и без, и даже если включить её
для **всех** цветов. Отключается пустым значением.

Оговорка: зелёных номеров в открытой галерее ~1%, и подтверждённых примеров у меня мало
(жёлтых не нашлось вовсе). Соответствие «H → жёлтые» выведено из описания серии, а не измерено.
Собрать свою цветную выборку и проверить: `python -m tools.eval_uz --fetch 30 --colors yellow,green`.

Посмотреть сырые выводы обеих голов на своих кропах: 

```bash
python -m tools.probe_model crops/*.jpg --chars          # оба вывода + уверенность по символам
python -m tools.probe_model photos/*.jpg --detect        # сначала YOLO, потом OCR
python -m tools.probe_model crops/*.jpg --all-variants   # перебрать варианты препроцесса
python -m tools.probe_model crops/*.jpg --expect 01A123BC
```

Скрипт печатает `anpr`, `ctype`, альтернативы и уверенность по каждому символу — по десятку
своих номеров сразу видно, что кодирует вторая голова.

**Препроцесс.** Тоже не записан в чекпоинте; по умолчанию взят дефолт DTRB: grayscale → resize
до 32×100 → `(x/255 − 0.5)/0.5`. Альтернатива с сохранением пропорций — `ANPR_PREPROCESS=pad`.
Прогоните `--all-variants` на своих кропах и оставьте вариант с лучшей точностью.

## Измеренная точность на реальных номерах УЗ

Галерея [platesmania.com/uz](https://platesmania.com/uz/) отдаёт вместе с каждым фото
«информер» — отрисованную пластину, в `alt` которой лежит **точный текст номера**. Это
готовый ground truth без ручной разметки, и на нём построен воспроизводимый бенчмарк:

```bash
python -m tools.eval_uz --fetch 80 --run      # скачать выборку и замерить
python -m tools.eval_uz --run --save-fails    # кропы ошибок в data/eval/fails/
python -m tools.eval_uz --compare models/*.pt # сравнить детекторы на одной выборке
python -m tools.eval_uz --run --imgsz 1280 --no-retry --conf 0.2   # свои настройки
```

Результат на 80 фото (оригиналы ~1500 px, CPU, настройки по умолчанию):

| Метрика | Значение |
|---|---|
| пластина найдена | **80/80 (100%)** |
| текст совпал символ-в-символ | **72/80 (90%)** |
| текст уложился в известный формат | 77/80 (96%) |
| время | 0.27 с/фото |

По классам номеров:

| Класс | Точность | Комментарий |
|---|---|---|
| `legal` (`01 084 LMA`) | 11/11 (100%) | |
| `private` (`01 A 111 AK`) | 60/64 (94%) | ошибки в одном символе на грязных и косых пластинах |
| `electric` (`01 M 018461`) | 1/1 (100%) | зелёный номер, формат найден по этой выборке |
| `trailer` (`4169 AA 70`) | 0/4 (0%) | **двухстрочные квадратные — чекпоинт их не умеет** |

Это же и подтверждает, что charset восстановлен верно: 72 номера прочитаны точно, без
систематических подстановок символов. Если бы порядок символов был угадан неправильно,
структура сохранялась бы, а буквы были бы не те.

Разбор всех 8 оставшихся ошибок (`--save-fails` + глаза): 4 двухстрочных прицепа,
1 ложная детекция (шильдик «MAN» на решётке грузовика вместо номера) и 3 ошибки в одном
символе на грязных/сильно косых пластинах.

### Отдельно по зелёным номерам

Цветные номера в галерее редки (~1 на 200 фото), поэтому для них есть отбор по цвету —
он определяется по маленькому «информеру», и большие фото качаются только для нужных:

```bash
python -m tools.eval_uz --fetch 30 --out data/eval-color --colors yellow,green --max-pages 90
python -m tools.eval_uz --run --out data/eval-color
```

Результат на собранных зелёных номерах (электромобили, формат `01 M 018461`):

| Метрика | Значение |
|---|---|
| пластина найдена | 5/5 (100%) |
| greedy как есть | 3/5 (60%) |
| **после правил** | **5/5 (100%)** |

Обе ошибки greedy — один и тот же промах: **последняя цифра прочитана как похожая буква**
(`01M02167O` вместо `01M021672`, `01M01846A` вместо `01M018461`). Это понятно: у зелёных
номеров шесть цифр подряд, а алфавит основной головы полон букв. Формат `uz_electric`
(`DD M DDDDDD`) снимает неоднозначность, и форматный отбор поднимает 60% → 100%.

Жёлтых номеров в открытой галерее не нашлось (просмотрено ~400 фото), поэтому по ним
замера нет — формат `uz_foreign` заведён по описанию серии, проверьте на своих данных.

**Про двухстрочные номера.** Прицепы и спецтехника в УЗ — квадратная пластина в две строки
(сверху `4169`, снизу `AA` и регион `70`). Я проверил это подробно: строки режутся корректно,
и после нормализации пропорций верхняя строка читается точно (`2373`, `2602`, `4169` — всё
верно), но нижняя (серия + регион в отдельной рамке, рядом флаг УЗ) всегда даёт мусор.
Вывод: **модель не видела таких пластин в обучении**, это не проблема препроцесса. Лечится
только дообучением — данные для него собираются автоматически (см. ниже).

Механика в коде осталась: `layout_variants()` читает и одну строку, и две, но альтернативная
раскладка побеждает **только** если её текст укладывается в формат номера УЗ. Поэтому она не
может ухудшить результат — после дообучения начнёт срабатывать сама.

> Ранее заявленные 97% / 87% — замеры автора на собственной тестовой выборке. Цифры выше —
> независимый замер на другой выборке, собранной из открытой галереи. Цифры выше — мой
> независимый замер на другой выборке (белые номера частных лиц и юрлиц, разные ракурсы),
> обвязка саму модель не меняет.

## Выбор YOLO: три детектора на одной выборке

Все три весов лежат в [models/](models/), скачиваются `python -m tools.fetch_yolo -m lpr n s`.
Сравнение — на тех же 80 фото узбекских номеров, остальное одинаково
(`python -m tools.eval_uz --compare models/*.pt`):

| Веса | Источник | Детекция | Текст | Формат | с/фото |
|---|---|---|---|---|---|
| **`yolo11n-plate.pt`** | morsetechlab/yolov11-license-plate-detection | 80/80 | **72/80 (90%)** | 77/80 | 0.31 |
| `lpr-yolov8n-plate.pt` | [Muhammad-Zeerak-Khan/…-YOLOv8](https://github.com/Muhammad-Zeerak-Khan/Automatic-License-Plate-Recognition-using-YOLOv8) | 80/80 | 66/80 (82.5%) | 75/80 | 0.30 |
| `yolo11s-plate.pt` | morsetechlab (размер s) | 40/40 | 32/40 (80%) | 36/40 | 0.40 |

**Про `lpr-yolov8n-plate.pt` (YOLOv8n из того репозитория).** Пластины он находит ровно так же
хорошо: 37/40 при `imgsz=640` без второго прохода и 80/80 со вторым — один в один с `yolo11n`,
и даже чуть быстрее сам детектор (60 против 66 мс/кадр). Но **боксы у него свободнее по
вертикали**: медианное соотношение сторон бокса 2.39 против 2.95 у `yolo11n` (у самой пластины
УЗ ≈ 4.3). Лишние поля сверху и снизу при ресайзе в 32×100 сжимают текст, и распознавание
теряет 6 номеров из 80:

| | правильно у обоих | только `yolo11n` | только `lpr` | ошиблись оба |
|---|---|---|---|---|
| номеров | 65 | 6 | 1 | 8 |

Пытался закрыть разрыв, не помогло:

- **подрезка вертикальных полей** по проекционному профилю текста внутри бокса: `lpr` 66→67,
  `yolo11n` 71→71. Один номер на 80 — не стоит кода, выбросил;
- **подгонка `crop_padding`**: `0.06` оказался оптимумом для **обоих** детекторов, любое
  отклонение хуже (`lpr`: 66 при 0.06, 63 при 0, 62 при 0.10, 51 при 0.20; `yolo11n`:
  71 / 66 / 68 / 55). То есть дефолт уже правильный, и разрыв не из-за него.

Вывод: модель из репозитория **рабочая и быстрая**, дело только в геометрии боксов под этот
конкретный распознаватель. По умолчанию оставил `yolo11n-plate.pt` как измеренный лучший,
переключение — одна переменная:

```bash
ANPR_DETECTOR_WEIGHTS=models/lpr-yolov8n-plate.pt
```

Важная оговорка: моя выборка — фото с platesmania (в основном фронтальные, при хорошем свете,
номер крупно). На ваших кадрах — камера под углом, ночь, движение — расклад может быть другим,
и `--compare` даёт ответ одной командой на **ваших** данных. Если у вас модель показала себя
лучше на реальных камерах, верьте своим данным, а не моим 80 фото.

Сквозной пайплайн на CPU: **~160 мс/кадр (~6 FPS)** на реальном видео, p95 = 277 мс.
Свой замер: `python -m tools.bench --video clip.mp4 -n 100`.

Три вещи, которые пришлось замерить и починить именно на видео (на фото их не видно):

| Что | Было | Стало |
|---|---|---|
| p95 задержки | 919 мс | **277 мс** |
| первый запрос после старта | ~930 мс | **183 мс** |
| один номер при съёмке на ходу | до **9 треков** и 4 дубля события | 1 трек, 1 событие |

- **Второй проход детектора выключен для видео** (`ANPR_DET_RETRY_IN_STREAM=false`). Он стоит
  366 мс, и на видео 15% кадров были без пластины — то есть каждый седьмой кадр платил за
  перепроверку. Для одиночного фото проход остаётся включённым: там второго шанса не будет.
- **Двухстрочные раскладки выключены** (`ANPR_TWO_LINE=false`). На видео 36% кропов уходили
  на двойное чтение — 184 мс против 97 при ровно том же наборе прочитанных номеров.
  Включать после дообучения на квадратных пластинах.
- **Прогрев моделей на старте**: первый форвард стоит 834 мс против 50-60 мс на следующих.
  Без прогрева эту задержку оплачивал первый клиент.

**Второй проход по пустому кадру.** На выборке УЗ детектор при `imgsz=640` терял 3 пластины
из 40 (номера грузовиков и прицепов — мелкие и под углом). Замеры на тех же трёх фото:

| Настройка | Найдено | Время/кадр |
|---|---|---|
| `imgsz=640, conf=0.35` | 0/3 | 60 мс |
| `imgsz=1280, conf=0.15` | 2/3 | 266 мс |
| **`imgsz=1536, conf=0.10`** | **3/3** | 397 мс |
| `yolo11s, imgsz=1280` | 1/3 | ~600 мс |

Поэтому по умолчанию включён второй проход: если на `640` не нашлось **ничего**, кадр
переснимается на `1536` с низким порогом. Платим только за пустые кадры — на выборке это
дало детекцию 40/40 при среднем времени 0.28 с/фото. В ответе есть флаг `timings.retried`.
Отключается через `ANPR_DET_RETRY_IMGSZ=0`.

Любопытно: `yolo11s` здесь **хуже** `yolo11n` — на 640 не нашёл ни одной из трёх. Так что
«модель побольше» тут не помогает, помогает разрешение.

### WebSocket

**`/ws/recognize`** — двусторонний поток кадров.

Клиент → сервер:
- бинарное сообщение = один кадр JPEG/PNG (самый быстрый путь);
- либо JSON `{"type":"frame","image":"data:image/jpeg;base64,...","frame_id":42,"ts":...}`;
- `{"type":"config","overlay":true,"track_events":false,"reset":true}` — настройки на лету;
- `{"type":"ping","ts":...}` → `{"type":"pong"}`.

Сервер → клиент: `{"type":"result", plates, timings, events, frame_id, server_ms, fps}`,
при `overlay:true` добавляется `overlay_jpeg_b64`.

**Backpressure сделан правильно:** в обработке всегда ровно один кадр, новый вытесняет
необработанный. Для живого видео это то, что нужно — задержка не растёт, вы всегда видите
свежий кадр, а не очередь пятисекундной давности. Инференс уходит в пул потоков, event loop
не блокируется.

**`/ws/streams/{id}`** — подписка на серверный поток (сервер сам читает RTSP).
**`/ws/events`** — только подтверждённые события со всех потоков.

```javascript
const ws = new WebSocket('ws://localhost:8000/ws/recognize');
ws.onmessage = e => {
  const m = JSON.parse(e.data);
  m.plates?.forEach(p => console.log(p.stable_text || p.text, p.conf, p.color));
  m.events?.forEach(ev => console.log('СОБЫТИЕ', ev.pretty));
};
canvas.toBlob(b => b.arrayBuffer().then(buf => ws.send(buf)), 'image/jpeg', 0.7);
```

## Что обвязка добавляет к точности модели

1. **Форматы номеров УЗ.** CTC даёт не только лучший путь; из top-k символов собираются
   альтернативы, и выбирается та, что укладывается в известный формат с валидным кодом региона
   (01–95). Пример из теста: greedy-вариант `01A1Z3BC` (0.90) проигрывает формату — выбирается
   `01A123BC` (0.80).
2. **Исправление путаницы символов** по позициям: в цифровых позициях `O→0`, `S→5`, `B→8`,
   в буквенных — наоборот. Помечается флагом `corrected`.
3. **Голосование по кадрам.** На видео одна пластина видна десятки кадров; голоса взвешены
   уверенностью, а валидный формат весит в 1.6× больше. Это главный выигрыш там, где
   one-shot ошибается: в тесте голосование вытянуло `01A777BC`, хотя отдельные кадры читались
   как `81A777BC`.
4. **Событие-уточнение.** Если после первых кадров голосование передумало, летит новое событие
   с `updated: true` и `previous`. Чтобы не было болтанки между похожими чтениями, новый лидер
   должен перевесить старый в `ANPR_EVENT_UPDATE_MARGIN` раз (по умолчанию 1.25).
5. **Цвет фона по HSV** — `white / yellow / green / blue / red / black`, независимо от OCR.
   Жёлтые и зелёные номера классифицируются по пикселям, а не по тексту, так что даже при
   ошибке чтения категория известна.

Форматы **сверены с 175 реальными номерами** из галереи platesmania — других структур там нет:

| Структура | Сколько | Пример | Класс |
|---|---|---|---|
| `DD L DDD LL` | 148 | `01 A 111 AK` | `private` — физлица |
| `DD DDD LLL` | 19 | `01 006 DFA` | `legal` — юрлица |
| `DDDD LL DD` | 8 | `4169 AA 70` | `trailer` — прицепы, **регион в конце**, две строки |

Последнее было сюрпризом: у прицепов код региона стоит **последним**, а не первым, — видно
и по фото, и по тексту с сайта. Поначалу у меня был regex с регионом впереди, теперь у
формата есть поле `region_group`, указывающее, где проверять код региона (01–95).

Ещё факт из весов, подтверждённый данными: буквы **`I` в номерах УЗ нет** (её класс в
`head_anpr` мёртвый), поэтому `LETTERS` — это `A-Z` без `I`. Это само по себе чинит частую
путаницу `1`↔`I`.

Форматы лежат в [app/core/plate_rules.py](app/core/plate_rules.py) и переопределяются файлом
`plate_formats.json` в корне — правьте под свои данные без правки кода:

```json
[
  {"name": "uz_private", "regex": "^(\\d{2})([A-HJ-Z])(\\d{3})([A-HJ-Z]{2})$", "plate_class": "private"},
  {"name": "uz_legal",   "regex": "^(\\d{2})(\\d{3})([A-HJ-Z]{3})$",          "plate_class": "legal"}
]
```

Из коробки заданы: `uz_private`, `uz_legal`, `uz_trailer` (сверены с данными), плюс `uz_moto`
и `uz_special` — этих двух в выборке не встретилось, они заданы по общей схеме и могут
потребовать правки. Если формат неизвестен, номер получает `valid: false` и
`plate_class: "unknown"`, но текст всё равно отдаётся.

## Дообучение под Узбекистан: датасет собирается сам

Готовой YOLO, обученной на узбекских номерах, в открытом доступе **нет** — я проверил:
на HuggingFace по запросам «uzbek/uzbekistan license plate» ноль моделей и датасетов, на
Roboflow Universe единственный узбекский проект — это 40 картинок. Поэтому вместо поиска —
инструмент, который собирает датасет сам, используя текст номера с platesmania как метку:

```
фото + текст номера (с сайта)
    -> YOLO находит пластину        -> бокс
    -> распознаватель читает кроп    -> текст
    -> текст совпал с сайтом?        -> ДА: бокс и кроп размечены гарантированно верно
```

```bash
python -m tools.build_dataset --fetch 300 --build --include-unverified
```

На выходе:

- `data/uz/dataset/` — YOLO-формат (`images/`, `labels/`, `data.yaml`, train/val 80/20
  детерминированным разбиением) для дообучения детектора под узбекские ракурсы и фон;
- `data/uz/recog/` — кропы + `gt.txt` (`путь<TAB>ТЕКСТ`) в формате
  deep-text-recognition-benchmark / EasyOCR. Здесь метки **настоящие**, с сайта, а не
  предсказанные — включая двухстрочные прицепы, которые сейчас не читаются;
- `data/uz/missed/` — фото, где пластина не найдена или OCR не совпал: их размечать руками.

Проверка на моей выборке из 40 фото: **35 меток подтверждены совпадением OCR**, 39 кропов
для распознавателя, 0 ненайденных. Команды для обучения скрипт печатает сам.

Честно о границах метода: авторазметка боксов — это самодистилляция, она учит новый детектор
тому, что старый **уже** умеет; пластины, которые детектор не находит, так не появятся (для
них и нужна папка `missed/`). А вот для **распознавателя** метки честные, поэтому именно там
дообучение даёт настоящий прирост — в первую очередь на двухстрочных прицепах (сейчас 0/4).

## Конфигурация

Все настройки — переменные окружения с префиксом `ANPR_` или файл `.env`
(полный список с комментариями — в [.env.example](.env.example)). Самое полезное:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `ANPR_DEVICE` | `cpu` | `cuda` — ускорение в 5-10 раз, менять только это |
| `ANPR_DETECTOR_WEIGHTS` | `models/yolo11n-plate.pt` | `...11s-plate.pt` — точнее, медленнее |
| `ANPR_DET_IMGSZ` | `640` | `960`/`1280` — лучше видит мелкие пластины |
| `ANPR_DET_CONF` | `0.35` | ниже — больше пластин и больше мусора |
| `ANPR_DET_RETRY_IMGSZ` | `1536` | второй проход по пустому кадру; `0` — выключить |
| `ANPR_TYPE_HEAD_COLORS` | `yellow,green` | цвета, для которых вывод `head_ctype` идёт в кандидаты |
| `ANPR_PREPROCESS` | `resize` | `pad` — сохранять пропорции кропа |
| `ANPR_MIN_VOTES` | `3` | кадров для подтверждения события: больше = точнее, но позже |
| `ANPR_WORKERS` | `2` | потоков инференса (несколько камер) |
| `ANPR_QUANTIZE` | `false` | int8 для LSTM/Linear: быстрее на CPU, точность проверьте сами |
| `ANPR_API_KEY` | пусто | если задан — нужен `X-API-Key` (в WS можно `?api_key=`) |

## Ограничения, о которых стоит знать

- **`charset` подтверждён на данных** (72/80 номеров прочитаны точно), но препроцесс всё ещё
  восстановлен, а не прочитан из чекпоинта. Прогоните `tools/probe_model.py --all-variants` на
  своих кропах: возможно, `pad` даст лучше, чем `resize`.
- **Двухстрочные квадратные номера (прицепы, спецтехника) не читаются** — 0/4 на выборке.
  Это ограничение чекпоинта, а не обвязки; данные для дообучения собирает
  `tools/build_dataset.py`.
- **`head_ctype` бесполезна на белых номерах** (измерено: 0/40 совпадений, для одной пластины
  на разных фото разный вывод). Гипотеза про жёлтые/зелёные — в разделе выше, включается
  через `ANPR_TYPE_HEAD_COLORS`, но мной не проверена: не нашёл таких номеров с известным текстом.
- **Форматы сверены с 175 номерами** из галереи platesmania (частные, юрлица, прицепы).
  Спецтипы — дипломатические, военные, транзит, мото — в выборку не попали, для них
  `uz_moto`/`uz_special` заданы по общей схеме; правьте `plate_formats.json`.
- **Цвет фона — эвристика по HSV, и она заметно врёт на реальных фото.** На выборке белые
  номера в тени уезжали в `black`, а пара — в `blue`. Для жёлтых/зелёных (крупный цветной фон)
  работает, но если цвет для вас критичен — калибруйте `_COLOR_BANDS` в
  [plate_rules.py](app/core/plate_rules.py) на своих кадрах.
- **Файловый источник** по умолчанию читается по кругу (`repeat: true`) — удобно для демо;
  для однократной обработки передайте `"repeat": false`, тогда поток встанет в `finished`.
- **GPU не тестировался** — на этой машине его нет. Код device-agnostic (`ANPR_DEVICE=cuda`),
  но замеры в README — только CPU.
